\section{Introduction}

This chapter covers the technical implementation of the MES-X dependency
traceability system. It describes how the proposed architecture was turned into
a working full-stack application that brings together work items, pull requests,
commits, branches, tags, sprint planning data, and AI-assisted review into a
single coherent workflow.

The chapter presents the technology stack, the delivery phases, the backend
module design, the frontend integration, the deployment setup, and the quality
practices used to validate the final product.

\section{Methodology Execution Through Delivery Phases}

\subsection{Methodology Selection}
\label{subsec:impl-methodology-selection}

Because this project combines evolving requirements, multi-service integration,
and short feedback loops with operational teams, selecting an appropriate
working methodology was a key project decision.

Three candidate methodologies were evaluated against the project context:

\begin{table}[H]
  \centering
  \caption{Comparative analysis of candidate project methodologies}
  \label{tab:methodology-comparison}
  \setlength{\tabcolsep}{4pt}
  \renewcommand{\arraystretch}{1.15}
  \begin{tabularx}{\linewidth}{|>{\raggedright\arraybackslash}p{2.9cm}|>{\raggedright\arraybackslash}X|>{\raggedright\arraybackslash}X|>{\raggedright\arraybackslash}p{3.0cm}|}
    \hline
    \textbf{Methodology} & \textbf{Main Advantages} & \textbf{Main Limitations} & \textbf{Fit for This Project} \\
    \hline
    Waterfall & Strong structure, clear documentation milestones, simple governance & Low adaptability to changing requirements, late feedback on integration issues & Limited fit \\
    \hline
    Kanban & Continuous flow, high flexibility, low process overhead & Weaker timeboxed milestones, less explicit iteration framing for internship checkpoints & Partial fit \\
    \hline
    Agile Scrum & Timeboxed iterations, frequent feedback loops, clear review cadence, risk reduction through incremental delivery & Requires disciplined backlog grooming and sprint planning & High fit \\
    \hline
  \end{tabularx}
  \setlength{\tabcolsep}{6pt}
  \renewcommand{\arraystretch}{1.5}
\end{table}

\textbf{Waterfall} offers strong phase-by-phase structure and clear
documentation gates, which is useful for stable projects with fixed scope.
However, it is less suitable here because dependency-traceability rules and
integration details had to be refined progressively based on intermediate
validation.

\textbf{Kanban} provides continuous flow, operational flexibility, and low
process overhead. Its main limitation for this project is weaker iteration
framing for milestone-based evaluation, which is important in an internship
context where progress must be demonstrated at regular checkpoints.

\textbf{Agile Scrum} combines iterative delivery, explicit planning horizons,
and regular review cycles. It supports incremental integration of backend,
frontend, and Azure DevOps connectors while allowing early correction of design
and implementation choices.

\subsection{Selection Rationale}
\label{subsec:impl-methodology-rationale}

Based on this comparison, \textbf{Agile Scrum} was selected as the primary
methodology. This choice was motivated by technical and organizational criteria:

\begin{itemize}
  \item the need to deliver working increments quickly (work-item tracing,
  pull-request resolution, commit/tag contextualization, sprint analysis);
  \item the need for frequent validation with end users and release engineers;
  \item the need to reduce integration risk through short implementation and
  test cycles;
  \item the need for visible milestone tracking across the internship timeline.
\end{itemize}

The enterprise environment already supported agile tooling through Azure DevOps
Boards, which made Scrum execution practical. Nevertheless, the methodology was
adopted for its demonstrated fit to project constraints and goals, not as an
unquestioned default.

\section{Backend Design}

\subsection{Module Architecture}

The backend is organized into six domain modules:

\begin{itemize}
  \item \textbf{Work Item:} single-root and batch traversal endpoints, SSE
  task streaming.
  \item \textbf{Pull Request:} linked work item retrieval by PR, PR summary
  enrichment.
  \item \textbf{Commit:} commit lookup by work item and PR, branch and tag
  context retrieval, batch tag resolution, commit review orchestration.
  \item \textbf{Sprint:} sprint listing by project, sprint work item retrieval
  for seeding batch analysis.
  \item \textbf{Decision:} aggregation service that synthesizes traceability
  outputs for decision support.
  \item \textbf{LLM:} prompt generation, guidance collection from repository
  instructions, external model invocation, response caching.
\end{itemize}

\subsection{API Design}

The backend exposes RESTful endpoints supporting single-root and batch
traceability with a consistent response model.

\begin{description}
  \item[\texttt{GET /workitem/:id/related}]
  Returns the traceability graph for a single root work item.

  \item[\texttt{POST /workitem/related}]
  Returns a deduplicated, aggregated graph for multiple root work items.

  \item[\texttt{GET /workitem/tasks/stream}]
  Streams processing progress using Server-Sent Events (SSE).

  \item[\texttt{GET /pullrequests/:prId/workitems}]
  Returns work items linked to a given pull request.

  \item[\texttt{GET /sprint?project=...}]
  Lists the iterations available for a project.

  \item[\texttt{GET /sprint/:sprintId/work-items?project=...}]
  Returns work items for a sprint; supports lazy loading in the UI.

  \item[\texttt{POST /commits/tags/batch}]
  Enriches commit references with repository tag metadata.

  \item[\texttt{POST /commits/hf/review}]
  Generates an AI-assisted review for a selected commit using commit and
  repository context.
\end{description}

DTO contracts across all endpoints prioritize stable response structures,
best-effort metadata enrichment, and a clear separation between traceability
payloads and AI-generated review content.

% ──────────────────────────────────────────────────────────────────────────────
\subsection{Processing Flows}

\begin{itemize}
  \item \textbf{Single-root:} resolve the root work item, traverse related
  nodes, enrich pull requests and commits, return a normalized graph.
  \item \textbf{Batch:} multi-root traversal with deduplication and
  consolidated counters.
  \item \textbf{Sprint:} load project sprints, lazily fetch sprint work items,
  forward selected items to the batch flow.
  \item \textbf{Commit tag:} resolve tag context in batch, grouped by
  repository, using a latest-tag strategy.
  \item \textbf{LLM review:} collect commit metadata and relevant file
  snapshots, augment the prompt with repository guidance, invoke the model,
  return the generated review to the decision dashboard.
\end{itemize}

\section{Deployment}

\subsection{Container Model}

The backend is packaged as an isolated Docker container with clearly defined
integration boundaries.

\begin{itemize}
  \item REST and SSE APIs are exposed on the configured runtime port.
  \item Runtime configuration and secrets are injected through environment
  variables and externalized config files.
  \item All communication with Azure DevOps is routed through the backend over
  HTTPS.
\end{itemize}

\subsection{Deployment Objectives}

\begin{itemize}
  \item Reproducible execution locally and in CI.
  \item Independent versioning and rollout of backend artifacts.
  \item Reduced deployment risk through clear component ownership.
\end{itemize}

\section{Quality and Security}

\subsection{Testing}

Validation was carried out at multiple levels:

\begin{itemize}
  \item \textbf{Backend unit tests (Jest):} controller and service behavior for
  the Work Item, Commit, and Sprint modules, including tag-selection utility
  functions.
  \item \textbf{Backend end-to-end test:} core HTTP integration behavior
  validated under the \texttt{test/} suite.
  \item \textbf{Frontend validation:} linting, static checks, and manual
  scenario testing of the main traceability screens and decision dashboard.
  \item \textbf{Cross-layer checks:} streaming behavior, repository grouping,
  and decision outputs verified end-to-end from backend to UI.
\end{itemize}

\subsection{Security Controls}

\begin{itemize}
  \item PAT-based authentication for all Azure DevOps API access.
  \item Backend-only routing of external API calls -- no direct frontend access
  to Azure DevOps.
  \item Secrets and credentials managed through environment configuration and
  secret store patterns.
  \item Read-only enforcement: the system issues no write operations to Azure
  DevOps artifacts.
  \item Structured logging to support incident analysis and diagnostics.
\end{itemize}

\section{AI-Assisted Development}

AI tools were used throughout the project to support both backend and frontend
work -- not to replace engineering decisions, but to speed up repetitive tasks,
improve review coverage, and enforce project conventions.

Both repositories keep automation artifacts versioned with the source code. The
backend \texttt{.github/agents/} directory defines dedicated agent roles:
architect, implementer, reviewer, and QA. The frontend \texttt{.github/}
folder captures UI guidelines, review rules, and reusable workflows for Vue,
Quasar, styling, and quality checks.

In practice, these agents assisted with code drafting, refactoring, test
scaffolding, documentation, and architecture reviews. On the backend they kept
DTO usage, controller-service separation, and observability patterns consistent.
On the frontend they reinforced guardrails around Vue Composition API usage,
token-based styling, and component quality.

The system also ships an operational LLM capability in the backend. The Commit
module delegates review requests to the LLM module, which builds prompts from
Azure DevOps commit metadata, selects relevant changed files, injects
repository guidance, and calls an external model to produce a structured review.
This review surfaces in the decision dashboard to complement release analysis
with code-level observations.

All AI-generated suggestions went through human review. Proposed changes were
treated as drafts and validated through linting, SonarQube policies, tests, and
developer inspection before being merged.

\section{Conclusion}

This chapter described how the MES-X traceability system was built from
infrastructure setup through to production deployment. The implementation
followed a phased delivery approach, with each module integrated and validated
incrementally. The result is a stable, maintainable platform that covers the
full traceability chain from sprint planning to commit-level review.
