\section{Introduction}

This chapter presents the technical implementation of the MES-X dependency
traceability system. It explains how the proposed architecture was translated
into a working full-stack solution that connects work items, pull requests,
commits, branches, and tags into one coherent analytical workflow.

The chapter begins with the technical stack, then describes the development
approach, the backend modules, the frontend integration, deployment concerns,
and the quality practices used to validate the delivered solution.

\section{Technology Stack and Architecture}

The MES-X implementation is built on a modern full-stack architecture designed
to support scalable dependency graph reconstruction and efficient traceability
analysis over large datasets.

\subsection{Implementation Phases}

The implementation of MES-X followed a continuous development and integration
strategy, where the system was progressively built module by module. Each
module went through the full software lifecycle: design, implementation,
testing, integration, and deployment.

This incremental approach ensured early validation of core components and
reduced integration risks by continuously aligning backend services, frontend
interfaces, and DevOps pipelines.

The development was organized into five major phases: Setup, Work Items,
Pull Requests, Commits, and Final Release.

The first phase focused on preparing the development environment and the core
delivery pipeline of the system.

\textbf{Main objectives:}
\begin{itemize}

  \item setup of local development infrastructure and database connections;
  \item initialization of CI/CD pipelines;
  \item creation of the frontend project structure and build pipeline.
\end{itemize}

\textbf{Key outcomes:}
\begin{itemize}
  \item fully operational development environment;
  \item automated build pipeline ready for integration;
  \item initial frontend architecture and design system foundation.
\end{itemize}

  \item validation and schema enforcement.
\end{itemize}

\textbf{Frontend implementation:}
\begin{itemize}
  \item Work Items listing and filtering interface;
  \item creation and editing forms;

\subsection{Module-Level Architecture}

The backend runtime is organized into domain-focused modules.

\begin{itemize}
  \item \textbf{Work Item module:} endpoints for single-root related traversal,
  aggregated batch related traversal, and SSE task streaming.
  \item \textbf{Pull Request module:} linked work item retrieval by PR and PR
  summary enrichment.
  \item \textbf{Commit module:} commit lookup by work item and PR, branch/tag
  context retrieval, and batch tag resolution.
  \item \textbf{Decision module:} aggregation service for decision-oriented
  synthesis on top of traceability outputs.
\end{itemize}

\subsection{API \textbf{Contract }Design}

The backend exposes a set of RESTful endpoints designed to support both
single and batch traceability analysis while maintaining a consistent
response model.

\begin{itemize}
  \item \textbf{Single related endpoint:} \texttt{/workitem/:id/related}  
  Returns a traceability graph centered on a single root work item.

  \item \textbf{Batch related endpoint:} \texttt{/workitem/related}  
  Returns an aggregated and deduplicated graph for multiple root items.

  \item \textbf{Tasks stream endpoint:} \texttt{/workitem/tasks/stream}  
  Uses Server-Sent Events (SSE) to stream processing results progressively.

  \item \textbf{PR-to-work-items endpoint:} \texttt{/pullrequests/:prId/workitems}  
  Retrieves work items linked to a given pull request.

  \item \textbf{Commit tag batch endpoint:} \texttt{/commits/tags/batch}  
  Enriches commit references with repository tag metadata.
\end{itemize}


The DTO strategy emphasizes:
\begin{itemize}
  \item stable response contracts between backend and service consumers;
  \item best-effort metadata enrichment (e.g., repository names for visited PRs);
  \item explicit counters and trace metadata for UI sorting and interpretation.
\end{itemize}
\subsection{Implementation Characteristics}
\begin{itemize}
  \item graph-oriented traversal with visited-state safeguards to avoid cycles;
  \item request-scoped caching and batched retrieval to reduce external API load;
  \item normalization of external payloads before service-to-service propagation;
  \item structured logging strategy for diagnosability and operational support.
\end{itemize}

\subsection{Sequence and Processing Flows}

The backend processing flow is centered on orchestration pipelines where each
service enriches the output of the previous stage.

\begin{itemize}
  \item \textbf{Single-root flow:} resolve root work item, traverse related
  nodes, enrich pull requests and commits, return normalized graph.
  \item \textbf{Batch flow:} aggregate multi-root traversal with deduplication
  and consolidated counters.
  \item \textbf{Commit tag flow:} resolve tag context in batch by repository
  grouping and latest-tag strategy.
\end{itemize}

\section{UI Implementation}


\subsection{UI Architecture and Main Surfaces}

The UI layer provides the operational entry point to the traceability system.
It is organized around route-driven views that correspond to the main analysis
scenarios and relies on a shared state and API integration layer to coordinate
requests, progressive loading, and result presentation.

\begin{itemize}
  \item \textbf{RelatedWorkItemTrace:} single-root analysis screen used to
  launch the exploration of one work item and inspect its related artifacts.
  \item \textbf{BatchWorkItemTrace:} task selection and loading screen used to
  progressively collect candidate work items through SSE streaming.
  \item \textbf{BatchRelatedWorkItemTrace:} aggregated result screen used to
  visualize the consolidated outcome of multi-root analysis with commit and
  repository context.
\end{itemize}

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{img/figures/uiroutes.png}

\caption{UI route/component architecture for traceability workflows}

\subsection{UI Data Flow and Backend Integration}

The UI communicates with the backend through a dedicated trace API layer and
maps backend contracts to typed frontend models.

\begin{itemize}
  \item Single analysis flow uses \texttt{/workitem/:id/related}.
  \item Batch task loading consumes \texttt{/workitem/tasks/stream} via SSE.
  \item Batch result enrichment uses \texttt{/commits/tags/batch} grouped by
  repository.
  \item Authentication failures are handled through controlled redirect
  behavior when backend returns unauthorized responses.
\end{itemize}

\section{Quality, Security, and Operational Considerations}

\subsection{Testing and Validation}

Validation was carried out at several levels to ensure that the delivered
solution remained consistent with the requirements defined earlier in the
report.

\begin{itemize}
  \item Backend unit tests were used to verify controller and service behavior,
  especially around work item traversal, commit resolution, and DTO mapping.
  \item End-to-end tests were used to validate the main API flows exposed by
  the backend and to confirm that the frontend consumed the contracts
  correctly.
  \item Frontend quality controls combined linting, style checks, and manual
  workflow validation for the main traceability views and the decision
  dashboard.
  \item Cross-layer checks were carried out to ensure that streaming behavior,
  repository grouping, and decision outputs remained coherent from backend to
  UI.
\end{itemize}

\textbf{Quality controls:}
\begin{itemize}
  \item controller-level input validation and typed DTO contracts;
  \item service-level tests for traversal, tag selection, and normalization;
  \item regression-focused tests for traversal and data normalization behavior.
\end{itemize}

\textbf{Security and runtime controls:}
\begin{itemize}
  \item secure communication for backend inbound and outbound integrations;
  \item managed external integration access to Azure DevOps;
  \item structured logging to support incident analysis and diagnostics.
\end{itemize}

\section{AI-assisted Development and Review}

AI-assisted tools were used throughout the project as a support mechanism for
both backend and frontend work. Their role was not to replace engineering
decisions, but to accelerate repetitive tasks, improve review coverage, and
formalize project-specific guardrails.

The two repositories keep their automation artifacts inside the codebase. On
the backend side, the `.github/agents/` directory defines dedicated roles such
as architect, implementer, reviewer, and QA agents. On the frontend side,
`.github/agents/`, `.github/instructions/`, and `.github/skills/` capture UI
guardrails, review rules, and reusable workflows for Vue, Quasar, styling, and
quality checks. Keeping these artifacts versioned with the source code made the
automation explicit, reviewable, and reproducible.

In practice, these agents were used to assist with code drafting, refactoring,
test scaffolding, documentation, and architecture reviews. The instructions
helped enforce conventions such as typed contracts, logging discipline,
component structure, localization, and style consistency. On the frontend, they
supported guardrails for Vue Composition API usage, token-based styling, and UI
quality checks. On the backend, they helped maintain consistency in DTO usage,
controller-service separation, and review expectations around observability and
integration patterns.

All AI-generated suggestions remained subject to human review. Proposed changes
were treated as drafts, then validated through linting, SonarQube policies,
tests, and direct developer inspection before integration. This approach made
AI assistance useful across the full stack while preserving accountability,
technical rigor, and architectural coherence.

\section*{Conclusion}

The implementation delivered a modular traceability platform that combines a
graph-oriented backend, an operational frontend, and deployment-ready runtime
configuration. The resulting system replaces a manual and fragmented analysis
process with a structured workflow that is faster, easier to interpret, and
better suited to the needs of release preparation.

By combining layered design, iterative development, quality validation, and
careful integration with Azure DevOps, the project established a maintainable
foundation for dependency analysis, release decision support, and future
extension of the traceability scope.
