\chapter*{General Introduction}
\addcontentsline{toc}{chapter}{General Introduction}
\markboth{General Introduction}{General Introduction}

\vspace{0.4cm}

Modern software teams rely heavily on structured traceability to understand how
work items, pull requests, commits, branches, and tags relate to one another.
Without a dedicated service, this investigation is manual, repetitive, and
error-prone. The \textbf{MES-X Dependency Management} project was born out of
exactly this need.

\medskip
The solution spans two repositories within the same workspace: the NestJS backend
in \code{mesx-proto-dependency-mgt-be} and the Vue\,3 trace UI in
\code{mesx-proto-dependency-mgt-ui}. The backend serves as the authoritative
integration layer with Azure DevOps, while the UI exposes the traceability
features through dedicated screens for single work items, batch task loading, and
batch related-item analysis.

\medskip
This was not a classic CRUD project. The objective was to build a read-only
dependency-management service capable of answering practical questions: which
commits are linked to a work item, which work items are linked to a pull request,
which branches and tags belong to a repository, how a work-item graph can be
traversed recursively, and how results can be rendered progressively in the
frontend.

\bigskip
\noindent This report is organized into ten chapters:

\begin{itemize}
  \item \textbf{Chapter 1 - General Presentation:} project context, objectives, repositories, and delivered scope.
  \item \textbf{Chapter 2 - Requirements and Architecture:} functional and non-functional constraints, module structure, and cross-repository flow.
  \item \textbf{Chapter 3 - Work Item Module:} endpoint design, recursive traversal, SSE streaming, and frontend usage.
  \item \textbf{Chapter 4 - Pull Request Module:} PR lookup, linked work-item resolution, and repository-summary enrichment.
  \item \textbf{Chapter 5 - Commit Module:} commit aggregation, branch and tag discovery, and batch tag resolution.
  \item \textbf{Chapter 6 - Decision Module:} aggregation input contract, classification rules, and repository-level decision output.
  \item \textbf{Chapter 7 - Azure DevOps Integration:} secret retrieval, configuration modules, Swagger, validation, and CORS.
  \item \textbf{Chapter 8 - Performance, Caching, and Reliability:} batching, concurrency limits, deduplication, and error handling.
  \item \textbf{Chapter 9 - Testing, Tooling, and Delivery:} tests, scripts, Docker, pipelines, and frontend integration.
  \item \textbf{Chapter 10 - Final Result and Conclusion:} outcome, lessons learned, limitations, and future improvements.
\end{itemize}

%% ── CONTEXT ────────────────────────────────────────────────────────────────
\section{Project Context}

Software teams that use Azure DevOps need to understand relationships between work
items, pull requests, commits, branches, and tags. Without a dedicated integration
layer, tracing these relationships requires navigating multiple Azure DevOps screens
manually - a time-consuming and error-prone process.

\medskip
The MES-X Dependency Management solution centralizes these relationships through a
consistent backend API and surfaces them through an operational trace UI with three
main screens:

\begin{itemize}
  \item a single work-item trace screen;
  \item a batch task-loading screen driven by SSE streaming;
  \item a batch related-results screen that aggregates graphs and enriches commits
        with tag context.
\end{itemize}

%% ── EXISTING NEED ───────────────────────────────────────────────────────────
\section{Study of the Existing Need}

Before building the solution, I identified the following concrete needs:

\begin{itemize}
  \item retrieve work items by ID with normalized relation data;
  \item navigate recursively from a root work item to its children and PR-linked items;
  \item stream large task result sets progressively rather than blocking the UI;
  \item resolve work items linked to a given pull request;
  \item retrieve commits linked to work items or pull requests;
  \item list repository branches and tags;
  \item resolve exact or surrounding tags for one or more commits;
  \item expose all of the above through a documented API and a usable trace UI.
\end{itemize}

%% ── PROBLEM STATEMENT ───────────────────────────────────────────────────────
\section{Problem Statement}

The core challenge is that relationship data in Azure DevOps is scattered across
several entity types and APIs. A work item may link directly to commits, indirectly
to pull requests, and recursively to child work items. The UI needs deterministic
and structured responses, not raw Azure DevOps payloads.

\medskip
The solution therefore had to:
\begin{itemize}
  \item connect to Azure DevOps securely and reliably;
  \item normalize heterogeneous data into stable DTO contracts;
  \item avoid duplicating work items, commits, and pull-request traversals;
  \item remain maintainable and testable as features were added;
  \item support both single-item and batch-oriented user flows.
\end{itemize}

%% ── PROPOSED SOLUTION ───────────────────────────────────────────────────────
\section{Proposed Solution}

To address these needs, I implemented a modular backend with four domain modules
and an integrated trace UI:

\begin{itemize}
  \item \textbf{Work Item Module} - work-item lookup, recursive related-item traversal, and SSE task streaming;
  \item \textbf{Pull Request Module} - PR-to-work-item resolution and repository-summary enrichment;
  \item \textbf{Commit Module} - commit aggregation, branch and tag discovery, single and batch tag resolution;
  \item \textbf{Decision Module} - post-processing aggregation that classifies work items and repository commits for decision support;
  \item \textbf{Trace UI} - three dedicated routes for single, batch-stream, and batch-related analysis.
\end{itemize}

%% ── DEVELOPMENT APPROACH ────────────────────────────────────────────────────
\section{Development Approach}

I followed an incremental approach: first securing the Azure DevOps connection
and configuration layer, then building the work-item flows, then pull-request
resolution, then commit and tag features, then implementing the decision
aggregation layer, and finally aligning the frontend trace flow with the actual
backend behavior.

\subsection{Methodological Choice}

An iterative workflow suited this project better than a one-shot implementation
because the modules are interdependent. Commit aggregation reuses work-item and
PR logic; the work-item traversal depends on relation parsing, PR expansion, cache
behavior, and commit aggregation. The Decision module then depends on structured
inputs produced by prior modules (work-item state sets and repository tag
position data), which reinforced the need for progressive validation. Developing
feature by feature allowed issues to be caught and corrected early.

\section{Introduction}

This chapter translates the identified needs into concrete requirements and

%% ── FUNCTIONAL REQUIREMENTS ─────────────────────────────────────────────────
\section{Functional Requirements}

The solution had to provide the following read-only capabilities:

\begin{itemize}
  \item get a work item by ID;
  \item traverse related work items recursively for one root;
  \item traverse multiple roots and return one aggregated response;
  \item stream task work items progressively through SSE;
  \item get work items linked to a pull request;
  \item get commits linked to a work item or pull request;
  \item list repository branches and tags;
  \item resolve exact or surrounding tags for a single commit;
  \item resolve exact or surrounding tags for a batch of up to 100 commits;
  \item aggregate decision input into done/other work-item sets and repository commit groups;
  \item expose all of the above through the trace UI.
\end{itemize}

%% ── NON-FUNCTIONAL REQUIREMENTS ─────────────────────────────────────────────
\section{Non-Functional Requirements}

Beyond feature delivery, the implementation had to respect the following
technical constraints:

\begin{itemize}
  \item clean separation between controllers, services, DTOs, and helpers;
  \item safe secret retrieval and external configuration loading via Dapr;
  \item bounded concurrency when expanding pull requests or resolving commits;
  \item deterministic, deduplicated result sets across all endpoints;
  \item explicit input validation and structured error responses;
  \item observability through a centralized logging layer;
  \item testability, documented API contracts, and reproducible delivery scripts.
\end{itemize}

\section{Relation Parsing}

The shared helper \code{extractLinks(...)} parses Azure DevOps relations and

checking whether the relation is an \code{ArtifactLink} whose URL contains
\code{PullRequestId}, and the PR ID is extracted from the decoded relation URL.

%% ── RECURSIVE TRAVERSAL ─────────────────────────────────────────────────────
\section{Recursive Related-Item Traversal}

The recursive graph traversal is the most important behavior of the module.
The implemented algorithm:

\begin{enumerate}
  \item normalizes the root work-item IDs and removes duplicates;
  \item loads the root items and fails early if one does not exist;
  \item initializes a discovered-ID set, a fetched-work-item cache, a PR-to-work-item cache, and a visited-PR set;
  \item traverses one level at a time through \code{traverseLevel(...)};
  \item fetches only the IDs not already present in the fetched-work-item map;
  \item extracts child work-item IDs from hierarchy links;
  \item extracts PR IDs, marks them as visited, and expands them through the Pull Request module;
  \item computes the next level of IDs while excluding already-discovered ones;
  \item recurses until no new IDs remain;
  \item aggregates commits after traversal is complete.
\end{enumerate}

%% ── PR EXPANSION ────────────────────────────────────────────────────────────
\section{PR Expansion and Concurrency}

Pull-request expansion is performed by \code{expandPullRequests(...)}. The
implementation uses \code{p-limit(5)} to cap concurrent PR expansions. Each PR
ID is resolved to work-item IDs through
\code{PullRequestService.getWorkItemIdsByPR(...)}. Results are cached in a
PR-to-work-item map and reused on later traversal steps.

%% ── SINGLE VS BATCH ─────────────────────────────────────────────────────────
\section{Single vs.\ Batch Related Endpoints}

Both response shapes share the same core payload: \code{visitedPullRequestIds},
\code{visitedPullRequests}, \code{commits}, and \code{commitCount}.

\begin{itemize}
  \item \code{GET /workitem/:id/related} returns one \code{RelatedWorkItemsResponseDto} with a single \code{workItemId};
  \item \code{GET /workitem/related} returns one \code{RelatedWorkItemsBatchResponseDto} with \code{requestedWorkItemIds} and a deduplicated payload across all roots.
\end{itemize}

\section{Conclusion}

The Work Item module is the backbone of the project. It provides the recursive

drive the rest of the system.

\chapter{Pull Request Module}

\section{Introduction}

This chapter explains how the Pull Request module resolves work items from
Azure DevOps pull requests and enriches the work-item traversal with repository
context.

\section{Implemented Endpoint}

\begin{center}
\code{GET /pullrequests/:prId/workitems}
\end{center}

\section{Core Responsibilities}

The Pull Request module fulfills two main responsibilities:

\begin{itemize}
  \item resolve the work items linked to a given pull request;
  \item enrich PR IDs with repository names through \code{getPullRequestRepositorySummaries(...)}.
\end{itemize}

\section{PR Lookup Strategy}

The helper \code{fetchPRById(...)} uses a fallback-aware lookup strategy:

\begin{enumerate}
  \item attempt \code{gitApi.getPullRequestById(...)} as the primary path;
  \item extract the repository ID from the result;
  \item if the primary call fails, fall back to \code{gitApi.getPullRequest(repoId, pullRequestId, project)};
  \item log warnings when fallbacks fail rather than crashing the whole flow.
\end{enumerate}

\section{Resolving Work Items Linked to a PR}

The workflow for \code{getWorkItemsByPR(...)} is:

\begin{enumerate}
  \item validate that the PR ID is numeric and positive;
  \item resolve the repository and PR metadata;
  \item retrieve raw work-item references using \code{getPullRequestWorkItemRefs(...)};
  \item remove duplicates from the returned ID list;
  \item fetch each work item with \code{WorkItemExpand.Relations};
  \item map results into \code{WorkItemResultDto} objects containing ID, title, and normalized links.
\end{enumerate}

\screenshot[Swagger UI showing the Pull Request endpoint - \texttt{GET /pullrequests/:prId/workitems} with example response]{Swagger documentation for the Pull Request module}

\section{Response Construction}

The public builder \code{getWorkItemsResponseDataByPR(...)} wraps linked work
items in a stable response that includes: the PR ID, the resolved project name,
the work-item count, and the list of linked work items.

\section{PR Repository Summaries}

The method \code{getPullRequestRepositorySummaries(...)} enriches visited PR IDs
with their repository names after traversal. The behavior is best-effort:

\begin{itemize}
  \item when the PR resolves, the real repository name is returned;
  \item when the PR cannot be resolved, the backend returns \code{unknown-repository};
  \item this allows the UI to display meaningful names when available and fall back to PR IDs when not.
\end{itemize}

\section{Conclusion}

The Pull Request module bridges Git-based pull requests and work-item
relationships, and provides the repository-summary enrichment now included in all
related-item trace responses.

\code{CommitWorkItemService.getCommitsByWorkitem(...)} works in two phases:

\begin{enumerate}
  \item load the work item and inspect its normalized links;
  \item collect direct commit links and pull-request IDs separately.
\end{enumerate}

The endpoint \code{GET /commits/pullrequests/:prId} delegates to the PR commit

directly by the UI for PR-centered traces and indirectly inside work-item commit
aggregation.

\section{Repository Branch and Tag Listing}

The endpoint \code{GET /commits/branches} resolves the repository ID, fetches
all references, separates branches from tags, strips the \code{refs/heads/} and
\code{refs/tags/} prefixes, and returns a \code{RepoReferencesResponseDto}.

\section{Single Commit Tag Resolution}

The algorithm inside \code{CommitHistoryService.getBranchesAndTagsByCommit(...)}:

\begin{enumerate}
  \item resolve the repository ID and fetch all refs;
  \item split refs into branches and tags;
  \item verify the target commit exists in the repository;
  \item resolve lightweight and annotated tag references to actual commit IDs;
  \item build a commit-to-tag map;
  \item scan the \code{main} branch first;
  \item if the commit is on \code{main}, return exact or surrounding tags immediately;
  \item otherwise, scan the remaining containing branches;
  \item if no tags are found anywhere, return the containing branch names as a fallback.
\end{enumerate}

\section{Batch Commit Tag Resolution}

The batch tag endpoint is one of the most impactful optimizations in the project.
The algorithm:

\begin{enumerate}
  \item rejects empty requests and requests larger than 100 commit IDs;
  \item resolves the repository ID and all branch and tag references;
  \item resolves tag references to their actual commit targets;
  \item builds a commit-to-tag map;
  \item creates a branch scan order with \code{main} first;
  \item scans branch histories recursively until all unresolved commits are found or all branches are exhausted;
  \item builds a result for each commit with \code{exactTags}, \code{tagAfter}, \code{tagBefore}, and \code{foundInBranch}.
\end{enumerate}

\screenshot[Batch tag enrichment result - commits grouped by repository with exact tags, before/after tags, and branch context]{Batch tag resolution results in the trace UI}

\section{Current UI Usage}

The batch-related frontend page groups discovered commits by repository and calls
\code{/commits/tags/batch} once per repository - not once per commit - giving
significantly better performance and a cleaner user experience.

\section{Conclusion}

The Commit module connects work-item and pull-request relationships back to
concrete code changes and repository references. It contains the most advanced
reference-resolution logic in the project.

\chapter{Decision Module}

\section{Introduction}

The Decision module is a post-processing layer that receives already-collected
work-item and commit-tag data, then computes a decision-oriented aggregation
payload. It does not query Azure DevOps directly; it classifies input data into
stable result groups that can be consumed by upper layers.

\section{Implemented Endpoint}

\begin{center}
\code{POST /decision/aggregate}
\end{center}

\section{Input Contract}

The endpoint consumes \code{DecisionInputSetDto} with two arrays:

\begin{itemize}
  \item \code{workItems}: objects with \code{id} and optional \code{state};
  \item \code{repositories}: objects with \code{repositoryName} and commit entries containing \code{commitId}, \code{tagBefore}, \code{tagAfter}, and \code{exactTags}.
\end{itemize}

\noindent Validation is enforced through class-validator decorators
(\code{IsDefined}, \code{IsArray}, \code{ValidateNested}, \code{IsString}, and \code{IsNumber}).

\section{Aggregation Rules}

\code{DecisionAggregateService.aggregate(...)} applies deterministic rules:

\begin{enumerate}
  \item split work items into \code{doneWorkItems} and \code{otherWorkItems} using case-insensitive \code{state == "done"};
  \item for each repository, inspect each commit's \code{tagBefore}, \code{tagAfter}, and \code{exactTags};
  \item classify commits into three groups: before-and-after, only-before, and only-after;
  \item set \code{considerForPR=true} for only-before commits when the same repository contains at least one commit with an after/exact tag;
  \item emit repository-level arrays for each classification bucket.
\end{enumerate}

\section{Output Contract}

The result \code{DecisionAggregateResultDto} contains five top-level arrays:

\begin{itemize}
  \item \code{doneWorkItems}
  \item \code{otherWorkItems}
  \item \code{reposWithBeforeAndAfter}
  \item \code{reposWithOnlyBefore}
  \item \code{reposWithOnlyAfter}
\end{itemize}

\noindent This shape gives consumers a direct decision-ready view without
recomputing tag-position logic on the client side.

\section{Controller and Error Handling}

\code{DecisionController} is exposed under \code{/decision}, tagged in Swagger,
and protected by \code{MesGenericErrorFilter}. The controller logs input size and
result counts. Service failures are logged and converted to
\code{InternalServerErrorException} with a stable error message.

\screenshot[Decision aggregation flow - input work items and repository commit-tag references are classified into done/other work-item groups and before/after repository buckets]{Decision module aggregation flow}

\section{Conclusion}

The Decision module complements Work Item, Pull Request, and Commit modules by
transforming technical trace data into a structured aggregation contract tailored
for decision support.

\chapter{Performance, Caching, and Reliability}

\section{Introduction}

This chapter explains the design choices that keep the service responsive and
predictable under realistic trace workloads.

\section{Batching Strategy}

Several operations are deliberately batched to reduce the number of API calls:

\begin{itemize}
  \item work-item fetching defaults to batches of 200 IDs;
  \item commit tag batch resolution rejects requests above 100 commit IDs;
  \item the frontend batch-related screen groups commit IDs by repository before calling the batch tag endpoint.
\end{itemize}

\section{Bounded Concurrency}

The project uses \code{p-limit} wherever unbounded parallelism could overload
Azure DevOps rate limits. Two clear examples:

\begin{itemize}
  \item PR expansion in the Work Item module with \code{p-limit(5)};
  \item PR commit expansion in the Commit module with \code{p-limit(5)}.
\end{itemize}

\section{Caching Strategy}

The backend contains two in-memory caches managed through \code{CacheManagerService}:

\begin{itemize}
  \item a work-item cache;
  \item a PR-to-work-item cache.
\end{itemize}

Both caches use FIFO-style eviction through \code{evictIfNeeded(...)} and are
capped at 1\,000 entries to prevent unbounded memory growth.

\section{Deduplication Strategy}

Deduplication is central to the correctness of every traversal. Maps and sets
are used at several levels:

\begin{itemize}
  \item root work-item IDs are normalized and deduplicated before traversal begins;
  \item discovered work items are tracked in a \code{Set<number>};
  \item visited PRs are tracked in a \code{Set<number>};
  \item fetched work items are stored in a map keyed by work-item ID;
  \item commits are deduplicated in a map keyed by commit SHA.
\end{itemize}

\section{Retry and Failure Handling}

The system includes several reliability measures:

\begin{itemize}
  \item each failed work-item batch is retried once before the request fails;
  \item PR expansion failures are logged and converted to empty sub-results when appropriate;
  \item missing work items produce explicit \code{NotFoundException} responses;
  \item invalid numeric identifiers are rejected early through validation helpers;
  \item the SSE stream broadcasts an error payload before closing clients when a failure occurs.
\end{itemize}

\section{SSE Stream Stability}

The streaming layer includes additional stability controls:

\begin{itemize}
  \item only one active stream is maintained at a time;
  \item new clients attach to the current stream if one already exists;
  \item all connected clients receive the same batch and completion payloads;
  \item the stream resets cleanly in both success and error cases.
\end{itemize}

\begin{infobox}[Current Architectural Gap]
The backend already exposes an aggregated batch related-items endpoint, but the
current UI batch results page still fans out single related-item requests per
selected root. This does not break functionality, but there is clear optimization
headroom for a future alignment pass.
\end{infobox}

\section{Conclusion}

Batching, bounded concurrency, cache management, deduplication, and defensive
error handling are the key reasons why the service remains usable even when the
trace graph becomes large and complex.

\chapter{Final Result and Conclusion}

\section{Final Delivered Result}

By the end of the internship, the MES-X Dependency Management solution
comprises:

\begin{itemize}
  \item a NestJS backend exposing stable, read-only endpoints for work items,
        pull requests, commits, branches, and tags;
  \item a Vue\,3 trace UI with single-item trace, batch task streaming, and

  \item shared contracts that include pull-request repository summaries through
        \code{visitedPullRequests};
  \item technical documentation aligned with the real implementation behavior.
\end{itemize}

\section{What I Learned}

This internship strengthened several practical skills:

\begin{itemize}
  \item backend design with NestJS and TypeScript;
  \item DTO design and response normalization;
  \item integrating with Azure DevOps through specialized APIs;
  \item secure secret retrieval with Dapr;

The current implementation is complete and usable. The following improvements

  \item align the batch related-results UI with the existing backend batch endpoint,

  \item extend frontend automated test coverage around the three trace flows;
  \item continue refining API documentation and operational examples for new consumers.
\end{itemize}

This internship project was valuable because it addressed a real traceability
problem with concrete engineering work. It delivered structured backend modules,
a usable trace UI, and a set of algorithms that connect work-tracking artifacts
back to pull requests, commits, branches, and tags.

keeping code, API contracts, UI behavior, and documentation in continuous
alignment is as important as the implementation itself. That discipline is what
makes a delivered solution maintainable by others long after the original
developer moves on.
